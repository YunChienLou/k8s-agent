# ADR-0003：人工「確認」不等於「授權」；寫入動作一律進入舊系統既有流程

- 狀態：已採納
- 日期：2026-09-28

## 背景

早期設計把 Copilot 上的人工確認稱為「審核／核准」，流程圖也畫成「使用者按下確認 → 執行」，
容易被理解成「使用者確認了，系統就放行」。這和企業實際的責任分工不符：
能不能執行，應該由擁有該業務的舊系統決定。

## 決策

1. **三層各司其職**
   - Agent：提出建議，不做決定
   - 使用者：**確認意圖**（「我要這樣做」），不能替系統放行
   - 舊系統：**判斷能否執行**（權限、狀態、金額上限、簽核規則），是唯一的決定者
2. **用語統一改為「確認」（confirmation）**，程式與文件中不再使用 approval／審核／核准描述 Copilot 端的動作。
   「核准／簽核」保留給舊系統內的業務流程。
3. **Agent 的寫入動作 = 在舊系統「提單」**：呼叫舊系統既有的申請單 API（例如改寄申請、補償申請），
   由舊系統原本的人員在**舊系統自己的畫面**上執行或簽核。Agent 不直接改變最終狀態。
4. **不複製業務規則**：Agent／Adapter 可以在卡片上顯示「預檢」結果，但只供參考；
   執行當下一律以舊系統的判斷為準，被拒絕時把原因轉述給使用者。

## 理由

- 責任歸屬清楚：申請人是使用者本人（JWT），執行人／簽核人是舊系統內的負責人員
- 不繞過既有內控：舊系統已有的簽核流程（例如補償超過上限需主管核准）照樣生效
- 規則只有一份：業務規則修改時，AI 端不需要同步修改
- 查證到確認之間可能相隔數分鐘，狀態可能改變（TOCTOU），只有執行當下的判斷可靠

## 標記「經由 AI 提出」

- 申請人仍記錄為使用者本人
- Demo：申請單使用既有的「來源管道」欄位，填入 `AI_COPILOT`
- 正式環境：以 token exchange（RFC 8693）取得帶 `act` claim 的 token，表示「Copilot 代使用者操作」

## 前提與取捨

- **前提是舊系統本來就有申請單／簽核流程**。若沒有，就不能宣稱零改動，
  只能改用外部通知（Email、Teams），或在舊系統前端加入少量程式
- 流程變長：使用者確認後還要等舊系統人員執行，Copilot 需要能顯示「已提單、待執行」的狀態，
  並在舊系統完成後更新（輪詢申請單狀態即可）

## 對 Demo 的影響

- 物流系統：`POST /api/redirect-requests` 建立改寄申請（待執行），物流人員在舊系統頁面按「執行」才變更地址
- 工單系統：補償在上限內直接建立；超過上限時建立**待主管簽核**的補償申請，而不是直接拒絕
- 兩個舊系統各加一頁「很傳統」的待辦清單（Thymeleaf），以輪詢顯示新申請單與「來源：AI Copilot」標記
