# ADR-0008：分層可移轉，門禁層可替換、辦事流程層自建（Build vs Buy）

- 狀態：已採納
- 日期：2026-09-28

## 背景

本專案的 Adapter 本質上是一個 MCP server。市面上已有 MCP gateway 產品
（雲端代管、開源自架皆有），提供 API 轉 tool、驗證、權限、稽核、限流、tool 白名單等功能。
MCP 規範仍在快速演進（例如 2026 年 7 月才將授權標準化），自建這些功能需要持續追規範。

同時，gateway 產品只處理「Agent 能不能安全地呼叫 API」，不處理「怎麼照公司原本的規矩把事情辦完」：
- 產品的核准是在 gateway 後台或 Slack 等另一條管道核准 **tool 呼叫**，與舊系統原本的簽核流程並行，
  結果不是繞過既有內控，就是同一件事被審兩次
- 核准人看到的是 tool 名稱與參數，缺乏業務脈絡與規章依據
- 單次呼叫之間彼此無關，無法處理跨系統部分完成
- 寫入身分常是 gateway 保管的服務帳號，而非使用者本人

## 決策

### 1. 三層切分

| 層 | 內容 | 策略 |
|---|---|---|
| **門禁層** | 驗證 token、token exchange（ADR-0007）、tool 白名單、權限控管、限流、稽核匯出 | 依標準介面自建，**預留替換為現成 gateway** |
| **Tool 定義層** | `tools.yaml`：任務型 tool、多支 API 組合、欄位裁切 | 宣告式定義，內容是業務知識，替換時轉換格式即可 |
| **辦事流程層** | 確認卡片、寫入送進舊系統既有簽核（ADR-0003）、規章 RAG 與引用驗證（ADR-0004、0005）、Saga（ADR-0006）、嵌入式 Copilot | **自建**，為本專案的核心價值 |

### 2. 可移轉的具體做法

- Agent 與 Adapter 之間**只使用 MCP + OAuth 標準**；Adapter 作為 OAuth resource server 並提供 Protected Resource Metadata。
  替換為任何支援 MCP 的 gateway，Agent 不需修改
- Tool 定義使用**宣告式 YAML**，不寫成程式
- 稽核以 **OpenTelemetry** 格式輸出，不綁定自有資料表結構
- 「使用者確認紀錄檢查」實作為**獨立的 policy hook**，不寫死在 Adapter；替換時接到產品的 policy 擴充點
- Copilot Agent **只能使用 MCP tool**，不提供 shell、程式執行或任意對外連線，避免繞過門禁層

### 3. Build vs Buy 判斷表

| 問題 | 偏向買現成 | 偏向自建 |
|---|---|---|
| AI 主要做什麼 | 查詢為主，或串接 SaaS 工具 | 寫入核心業務系統 |
| 舊系統簽核流程 | 沒有或很簡單 | 有，且為內控重點 |
| 部署限制 | 可上雲，可用代管 gateway | 只能地端：代管產品不可用，只剩開源自架或自建 |
| 系統與 tool 數量 | 很多且持續增加 | 少數核心系統 |
| 維運人力 | 無專責平台團隊 | 有團隊可長期維護 |
| 稽核要求 | 一般 | 金融、保險、醫療等，須追溯到規章依據 |

**建議組合**：門禁層能上雲就用代管產品、只能地端就用可自架的開源 gateway，都不適合才自建且只做最小範圍；辦事流程層自建。

## 本專案的選擇與理由

- 門禁層**這次選擇自建**：目的是理解驗證、token exchange、稽核的原理；但嚴格依標準介面設計，可替換
- 辦事流程層自建：這是產品無法提供、且與企業內控綁定的部分

## 取捨

- 自建門禁層需追隨 MCP 規範變動；以標準介面與分層降低替換成本
- 替換為產品時，policy hook 與 tool 定義需依產品能力轉換，可能無法一對一對應
