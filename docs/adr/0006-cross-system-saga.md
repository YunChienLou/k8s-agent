# ADR-0006：跨系統動作以 Saga 處理部分完成

- 狀態：已採納
- 日期：2026-09-28

## 背景

一個 Agent 建議可能跨多個舊系統，例如「改寄（物流系統）＋補償改寄運費（工單系統）」。
依 ADR-0003，每個寫入都是在各舊系統開單，由不同的人員各自審核執行，因此可能出現
**一張單已執行、另一張被退件或遲遲未處理**的部分完成狀態。

各舊系統有各自的 DB，且流程中夾著可能長達數小時的人工審核，
**無法使用分散式交易（2PC）或長時間鎖定資源**。

此問題在導入 AI 前就存在（人工在兩個系統各開一張單，同樣可能一過一退），
AI 層不會使其惡化，但可以讓它被追蹤、被處理。

## 決策

採用 **Saga 模式**：每一步各自提交，由 Agent 追蹤整體狀態，出現部分完成時以補償動作或人工決定收斂。

### 1. 先判斷依賴關係

- 為每個建議中的動作標註依賴：例如「補償改寄運費」依賴「改寄成功」
- 互相獨立的動作（例如寫工單備註）可並行，失敗互不影響

### 2. 有依賴的動作依序提單，不並行

- 前一步**執行完成**後才提交下一步
- 排序原則：**最可能被拒絕、最難撤回的步驟放前面**；容易撤回的放後面
- 多數部分完成可藉排序避免

### 3. 部分完成時，交由人決定

- Copilot 卡片呈現現況與選項，例如：「改寄已執行，補償被退件（原因：超過權限上限）。要撤回改寄，還是改送主管簽核？」
- **不自動執行補償**：撤回已執行的業務動作本身需要判斷
- 補償動作同樣走舊系統既有流程（撤單 API 或反向申請單），並受 ADR-0003 約束

### 4. 逾時

- 每張申請單設定 SLA（demo：4 小時），逾時未處理則提醒發起人或主管
- Saga 不可無限期等待

### 5. 狀態追蹤與真實來源

- Saga 狀態由 Agent 以 LangGraph + Postgres checkpointer 保存：`proposed → submitted → executed | rejected | expired → compensated`
- **舊系統才是真實來源**：Agent 的狀態是追蹤用副本，定期輪詢舊系統核對，以舊系統為準

### 6. 冪等性

- 重試不得重複開單
- 舊系統申請單若有「外部單號」欄位，填入確認編號作為冪等鍵
- 若無此欄位，Adapter 重送前先查詢是否已建立

## 已知限制

若業務要求多個動作**必須同時成立**，而舊系統本身未提供合併流程，
AI 層**無法憑空創造原子性**，只能做到追蹤、補償與人工介入。
此類需求應回到舊系統端提供合併流程。

## 對 Demo 的影響

- 主情境改為依序提單：改寄申請執行完成後，才提交補償申請
- 新增情境：物流人員退回改寄申請 → Copilot 顯示部分完成，補償申請不會送出
