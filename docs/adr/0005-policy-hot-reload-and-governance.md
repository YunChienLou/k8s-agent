# ADR-0005：規章熱部署與治理

- 狀態：已採納
- 日期：2026-09-28

## 背景

規章與 SOP 會持續新增、修改。若每次變更都要重新部署 Agent 或重新訓練模型，規則更新會嚴重落後。
ADR-0004 已決定以 RAG 提供規章依據；本 ADR 決定規章**如何在不重新部署的情況下生效**，以及**如何避免錯誤規則即時影響 Agent**。

## 決策

### 1. 規章只存在資料庫，不存在程式或 prompt

- 所有規章一律經 RAG 檢索取得，**不寫進 system prompt**（寫進 prompt 就必須重新部署才能更新）
- Agent 每次查詢都讀取當下資料，因此新增或修改規則**不需重新部署任何服務**

### 2. 規章來源與同步流程

- **來源**：既有知識庫系統（demo 中為 legacy namespace 的知識庫），不另建一套規章管理系統
- **同步 job**：偵測來源發布事件（webhook 或輪詢）→ 按條文切塊 → 地端 embedding → 寫入 pgvector
- Embedding 模型固定（ADR-0004）；更換 embedding 模型需整批重建索引，**不屬於熱部署範圍**

### 3. 版本與生效期間

每個 chunk 帶有：

| 欄位 | 用途 |
|---|---|
| `doc_id`、`article_no` | 辦法與條號，引用出處用 |
| `version` | 規章版本 |
| `status` | `draft`／`published`／`retired` |
| `effective_from`、`effective_to` | 生效期間 |

- **發布是原子切換**：同一個 transaction 內將新版設為 `published`、舊版填入 `effective_to`，不會出現新舊混雜
- 檢索只取 `published` 且在生效期間內的條文 → **預先發布、未來日期生效的規則會自動生效**
- **回滾** = 將狀態切回舊版
- 若有檢索快取，發布時遞增索引版本號，使舊快取失效

### 4. 治理：規則能即時生效，錯誤也會即時生效

- **發布前審核**：由法遵或主管核准才能發布，建議雙人覆核（防止 knowledge poisoning）
- **回歸測試**：每條規則對應至少一個評測案例；發布前自動執行受影響的評測，失敗則阻擋發布
- **可追溯**：稽核 log 記錄每次建議引用的 `chunk id` 與 `version`，事後可證明 Agent 當時依據哪一版規定
- 舊版本保留不刪除，供稽核還原

### 5. 與舊系統程式內規則的一致性

- RAG 規章可熱部署，但**舊系統程式內的規則不行**（例如補償上限寫在程式中）
- 兩者不一致時以舊系統為準（ADR-0003）：Agent 可能依新規章提出建議，送出後被舊系統拒絕——這是預期行為，不是錯誤
- 發布規章時提供**一致性檢查提醒**：若條文涉及舊系統已實作的規則（以標籤標註），通知相關系統負責人同步修改

## 取捨

- 發布審核與回歸測試會拉長規則生效時間，但換得可控性
- 同步 job 失敗時，Agent 仍使用上一個已發布版本，需要監控同步延遲

## 備註

以既有知識庫作為規章來源，符合「不為 AI 改動舊系統」的原則（ADR-0001）：知識庫照常發布，同步 job 從外部讀取。
